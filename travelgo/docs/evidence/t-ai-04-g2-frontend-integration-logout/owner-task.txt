## 3. G2 API INTEGRATION

Tích hợp đúng các endpoint hiện có:

- GET `/api/agent/verified-history/privacy`
- POST `/api/agent/chat`
- POST `/api/agent/verified-history/:id/reset`
- DELETE `/api/agent/verified-history/:id`
- DELETE `/api/agent/verified-history`

Dùng chính xác request/response schema trong source.

G2 request phải có:

- Server-created conversation ID sau start.
- Correct action start/continue.
- Fresh UUID requestId.
- Exact latest revision.
- Required consentVersion.
- Current user message.

Không gửi:

- Client-supplied history để cấp proof.
- Client-generated conversation owner.
- User ID tùy ý.
- Verified slots tự dựng từ frontend.
- Tool arguments tự thêm.
- Bypass hoặc skip-completeness flags.

Frontend có thể giữ message history để hiển thị, nhưng không được coi nó là verified server context.

Không nhận metadata từ error của session khác hoặc từ dữ liệu client không được xác minh.

## 7. SAFE CONFIRMATION UX

Đây là phần ưu tiên để xử lý giới hạn NLU hiện tại.

Tình huống:

User đã chọn xe máy nhưng Qwen3 vẫn trả needs_input transportation.

UI không được mặc định hiển thị:

"Bạn chưa chọn phương tiện."

Thay bằng câu trung lập, ví dụ:

"Agent đang yêu cầu bạn xác nhận lại phương tiện."

Nếu missingFields có transportation, có thể hiển thị hai lựa chọn:

- Xe máy
- Ô tô

Chỉ khi người dùng chủ động bấm lựa chọn:

Xe máy → gửi current message mới:

`Phương tiện: motorbike`

Ô tô → gửi:

`Phương tiện: car`

Phải gửi qua G2 request bình thường:

- Fresh requestId.
- Latest revision.
- Same owned conversation.
- Normal quota.
- Original backend validation.

Không auto-resend khi AI hỏi lại.

Không tự chuyển raw clarify thành tool.

Không tự gọi Planner.

Không dùng bare `motorbike` như một short patch chưa được grammar hỗ trợ.

Nếu người dùng đã xác nhận mà Agent vẫn hỏi lại, phải cho phép:
- Nhập thông tin bằng tay.
- Thay đổi lựa chọn.
- Reset cuộc hội thoại.
- Hủy phiên.

Không tạo vòng lặp tự động gửi cùng nội dung.

Không quảng cáo explicit confirmation là chắc chắn chữa mọi raw NLU failure.

## 8. REQUEST ID, REVISION VÀ CONCURRENCY

Mỗi logical request mới cần fresh UUID.

Không reuse requestId khi người dùng thử lại sau lỗi.

Không tự retry inference để vượt timeout hoặc quota.

Prevent duplicate submit khi một G2 turn đang active.

Khi backend trả 409:
- Không ghi đè current session bằng stale revision.
- Hiển thị trạng thái phù hợp.
- Cho user refresh/reset/restart theo contract.

Khi người dùng chuyển tài khoản hoặc logout:
- Hủy/fence các request đang pending khi có thể.
- Increment local auth/session generation.
- Không render response cũ vào phiên người dùng mới.

Không dùng last-response-wins.

## 9. RESET, EXPIRY, RELOAD VÀ LOGOUT

### Reset

Gọi endpoint reset với ownership và correct active session.

Clear chat context/pending actions theo response backend.

Không giữ verified fields cũ trong UI như state đang còn hiệu lực.

### Revoke session

Cho phép kết thúc G2 session bằng endpoint revoke one.

Clear active ID/revision ở frontend.

### Expiry/restart

Nếu backend trả session unavailable:
- Không tự tái tạo verified state từ client messages.
- Cho user bắt đầu session mới.
- Giải thích phiên cũ không còn khả dụng.

Trang reload phải có behavior rõ ràng, được test; không khẳng định server state vẫn còn nếu không có cách khôi phục được xác thực.

### Logout

Trong luồng logout:

1. Ngừng/fence Agent requests.
2. Nếu có authenticated G2 context, thử gọi revoke-all hoặc revoke relevant owned sessions khi token còn hợp lệ.
3. Clear client Agent state.
4. Clear auth session theo flow hiện hành.

Revoke là best effort, không được ngăn người dùng đăng xuất chỉ vì mạng lỗi.

Nếu revoke thất bại:
- Không hiển thị lại dữ liệu của tài khoản cũ.
- Không nói server đã xóa thành công.
- Không nói JWT đã bị revoke.
- Server TTL vẫn là giới hạn retention dự phòng.

Chú ý các race giữa logout, request pending và account switch.
